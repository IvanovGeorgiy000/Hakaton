# СтройКонтроль — бэкенд

API сервиса мониторинга строительных площадок по видео с камер (ЛЦТ 2026, команда «Работяги»).
Видео камеры → кадр каждые 2 секунды → техника на кадре → сверка с этапом календарного плана → предупреждение об отклонении.

**Стек:** Python 3.12+, FastAPI, SQLAlchemy 2 (async), Pydantic v2, httpx, Pillow, ffmpeg; шлюз видео mediamtx;
распознавание техники — своя модель YOLO в ONNX Runtime; SQLite локально, PostgreSQL в Docker; менеджер пакетов `uv`.

## Запуск

```bash
cd backend
uv sync                                             # зависимости
uv run uvicorn app.main:app --port 8100 --reload    # API: http://localhost:8100, Swagger: http://localhost:8100/docs
bash ../tools/video-gateway.sh                      # в соседнем терминале — шлюз видео (brew install mediamtx; нужен ffmpeg)
```

При первом запуске сервер создаёт таблицы миграциями (см. [«Модель данных»](#модель-данных)) и наполняет пустую базу
демонстрационными данными. Время в них считается от момента запуска, поэтому стенд всегда выглядит «сегодняшним».
Пересоздать базу: `uv run python -m app.seed --reset`.

Весь стенд в Docker (PostgreSQL + шлюз видео + API + интерфейс): из корня репозитория `docker compose up --build`,
интерфейс — http://localhost:8080.

Проверки: `uv run pytest` (123 теста, сеть и шлюз не нужны; те же тесты на PostgreSQL — с переменной `SK_TEST_DATABASE_URL`
и `uv run --extra postgres pytest`),
`uv run ruff check . && uv run ruff format --check .`.

### Вход

| Логин | Роль | | Логин | Роль |
|---|---|---|---|---|
| `prorab` (и `prorab2…4`) | прораб, свой объект | | `inspektor` | инспектор |
| `rukovoditel` | руководитель проекта | | `admin` | администратор — может всё |

Пароль стенда задаётся переменной `SK_DEMO_PASSWORD` (по умолчанию `demo`) при наполнении базы. В демо-режиме
(`SK_DEMO_MODE=true`) работает вход по роли без пароля: `POST /api/auth/demo-login`. Права проверяет сервер: прораб видит
только свой объект (и его видео), но не отмечает, сколько сделано по факту; предписания закрывает инспектор; объекты
(с планом и зонами) заводят и настраивают руководитель проекта и администратор, они же отмечают выполнение работ
и подключают камеры; администратор
может всё, что остальные роли, плюс удалять объекты и камеры, управлять сотрудниками и правилами.

## Настройки

Все переменные начинаются с `SK_`, полный список с пояснениями — в [.env.example](.env.example). Главное:

| Переменная | Назначение |
|---|---|
| `SK_DATABASE_URL` | по умолчанию SQLite в `data/`; для PostgreSQL — `postgresql+asyncpg://…` и `uv sync --extra postgres` |
| `SK_SECRET_KEY` | подпись токенов, шифрование паролей камер, служебная учётка шлюза — **поменяйте вне стенда** (без демо-режима сервер со стандартным ключом не запустится) |
| `SK_VIDEO_API_URL`, `SK_VIDEO_RTSP_URL`, `SK_VIDEO_WEBRTC_URL` | шлюз видео: API, RTSP для сервера, WebRTC для браузера |
| `SK_FRAME_INTERVAL_S` | раз во сколько секунд кадр с каждой камеры уходит на анализ (по умолчанию 2) |
| `SK_CHECK_INTERVAL_S` | раз во сколько секунд объект сверяется с планом (по умолчанию 60) |
| `SK_ANALYSIS_PROVIDER` | `auto` (по умолчанию) — своя модель, если файл на месте; `mock` — демо-анализатор, `http` — внешний сервис распознавания, `push` — сервис сам присылает детекции |
| `DETERMINISTIC_SERVICE_URL`, `VLM_LLM_SERVICE_URL`, `ANALYTICS_SERVICE_TOKEN` | сервисы аналитики коллеги — см. [«Работы по камерам»](#работы-по-камерам-сервисы-аналитики-коллеги-frame-analysis-v1) |

## Видео: шлюз и конвейер

```
камера (RTSP) ──► шлюз mediamtx ──► браузер (WebRTC/WHEP, задержка ~0,5 с)
                        │
                        └──► сервер: ffmpeg берёт кадр раз в 2 с ──► модель ──► в памяти: что видит каждая камера
                                                                                   │
                             раз в минуту — сверка объекта ◄─────────────────────────┘
                             (в базу — по кадру на камеру: доказательства и история для поиска простоя)
```

- **Шлюз** ([infra/mediamtx/mediamtx.yml](../infra/mediamtx/mediamtx.yml)) ничего не знает о камерах заранее: сервер сам заводит
  поток `cam-<id>` на каждую включённую камеру через API шлюза ([app/services/video.py](app/services/video.py)) и сверяет
  их раз в 30 секунд (шлюз мог перезапуститься). Пароль камеры остаётся на сервере и в шлюзе, браузер его не видит.
- **Кто может смотреть**, шлюз спрашивает у сервера перед каждым подключением: `POST /api/video/auth`. Браузер передаёт тот же
  токен, что и в API (заголовок `Authorization`), и видит только камеры своих объектов. Публиковать в шлюз и брать кадры на
  анализ может только сам сервер (служебная учётка, пароль выводится из `SK_SECRET_KEY`).
- **Конвейер** ([app/services/pipeline.py](app/services/pipeline.py)): на каждую камеру — процесс ffmpeg, который берёт из её
  потока кадр раз в `SK_FRAME_INTERVAL_S`. Каждый кадр разбирает анализатор; не успевает — берётся самый свежий кадр,
  очередь не копится. Раз в `SK_CHECK_INTERVAL_S` объект сверяется с правилом: для каждой камеры берётся кадр с самым частым
  за минуту набором техники (одиночная ошибка распознавания не делает погоды).
- **Что видит анализ прямо сейчас** — `GET /api/live`: интерфейс рисует это рамками поверх видео.
- **Демо-ролики.** Сервер сам публикует ролики из `app/assets/clips/*.mp4` в шлюз как RTSP-потоки `demo-feed-<ролик>`.
  Демо-камеры — обычные RTSP-камеры, смотрящие на такие потоки; в форме «Добавить камеру» их адреса есть в быстрой настройке.
  Ролики — съёмка со строек с Wikimedia Commons, авторы и лицензии — в [app/assets/clips/CREDITS.md](app/assets/clips/CREDITS.md).

## Анализ кадров: своя модель распознавания

Анализ спрятан за интерфейсом `AnalysisProvider` ([app/services/analysis/](app/services/analysis/)). Остальной код не знает, кто именно нашёл технику.
`SK_ANALYSIS_PROVIDER`:

- **`auto`** (по умолчанию) — своя модель, если файл `models/detector.onnx` на месте, иначе демо-анализатор.
- **`local`** — своя модель; без файла модели сервер не запустится (молча подменять распознавание демо-разметкой нельзя).
- **`mock`** — демо-анализатор. Для демо-камер отдаёт разметку ролика, который камера показывает
  (`app/assets/clips/annotations.json`); фото (ручная проверка, страница `/demo`, история демо-базы) узнаёт по «отпечатку»
  изображения (`app/assets/seed/annotations.json`). Незнакомый кадр честно помечается как нераспознанный: выдуманных рамок нет.
- **`http`** — каждый кадр (раз в 2 секунды с каждой камеры) уходит во внешний сервис. Включается двумя переменными:

  ```bash
  SK_ANALYSIS_PROVIDER=http SK_ANALYSIS_API_URL=http://ml-host:8200/analyze
  ```

### Своя модель

[app/services/detector.py](app/services/detector.py). Сейчас — **YOLO26m, дообученная на датасете MOCS** (Moving Objects in
Construction Sites, 13 классов; mAP50 = 0,83 на проверочной выборке). Считается прямо в сервере через ONNX Runtime — без
PyTorch, файл модели 41 МБ. На Mac — через CoreML (≈ 30–40 мс на кадр на M4; на процессоре — ≈ 70 мс), на Linux и в Docker —
на процессоре, с `onnxruntime-gpu` — на видеокарте. В Docker Desktop на том же M4 кадр ≈ 0,2 с: у виртуальной машины нет
CoreML, а процессор в ней медленнее, — для показа на Mac запускайте бэкенд без Docker. Ответы модели на сервере совпадают с Ultralytics: кадр уменьшается
тем же способом, что при обучении, отбор рамок — тот же (кроме одного: он общий для всех классов, чтобы одна машина
не давала две рамки разных типов).

Какие классы модели — техника ТЗ, сервер решает по их названиям (они записаны в самой модели):

| MOCS | Техника |
|---|---|
| Excavator | экскаватор |
| Truck | самосвал (в MOCS отдельного самосвала нет — Truck там почти всегда самосвал) |
| Roller | каток |
| Bulldozer | бульдозер |
| Crane | автокран |
| Concrete mixer | бетоносмеситель |
| Worker, Static crane, Hanging head, Loader, Pump truck, Pile driving, Other vehicle | не техника ТЗ — рамки не показываем |

Кран-манипулятора и грузовика в MOCS нет — эта модель их не найдёт. Если у новой модели классы называются иначе, соответствие
задаётся без правки кода: `SK_DETECTOR_CLASSES='{"Tipper": "dump_truck", "Pump truck": ""}'` (`""` — не показывать).
Ещё настройки: `SK_DETECTOR_CONFIDENCE` (0,35 — рамки увереннее показываем и учитываем), `SK_DETECTOR_MODEL` (путь к файлу),
`SK_DETECTOR_ACCELERATE=false` — считать только на процессоре, `SK_DETECTOR_THREADS` — ядер на модель.

**Новая версия модели.** От разработчика модели достаточно файла `.pt` (Ultralytics). Перевести в ONNX — один раз, PyTorch
ставится только на время команды:

```bash
uv run --with "ultralytics>=8.4" --with onnx --with onnxslim python -m tools.export_model ~/Downloads/best.pt --title "MOCS YOLO26m v2"
```

[tools/export_model.py](tools/export_model.py) кладёт модель в `models/detector.onnx` (вход 640×384 — под кадры 16:9,
веса во float16 — файл вдвое меньше) и сверяет ответы получившегося файла с исходной моделью на демо-фото. Потом перезапустите
сервер. Выход YOLO26 «без NMS» (`nms=False`) у дообученной модели заметно хуже обычного — инструмент берёт обычный.

### Контракт сервиса анализа

```
POST {SK_ANALYSIS_API_URL}            multipart/form-data
  image      кадр JPEG 1280×720
  camera_id  идентификатор камеры (необязательно)
  taken_at   время кадра, ISO 8601 (необязательно)
Authorization: Bearer {SK_ANALYSIS_API_KEY}    — если ключ задан

200 application/json
{ "model": "yolo11m-construction-v1",
  "detections": [ { "type": "excavator", "confidence": 0.94,
                    "box": { "x": 24.5, "y": 41.5, "w": 46.5, "h": 57.0 } } ] }
```

`type` — один из `excavator, dump_truck, roller, manipulator, mixer, bulldozer, truck, crane` (неизвестные типы пропускаются).
`box` — проценты от кадра, `x`/`y` — левый верхний угол. Готовая заготовка такого сервиса с примером для YOLO:
[tools/analysis_stub.py](tools/analysis_stub.py).

**Push-режим** (`SK_ANALYSIS_PROVIDER=push`). Если сервис анализа сам забирает видео (например, из шлюза), он присылает готовый
результат: `POST /api/ingest/snapshots` (`camera_id`, `detections` — JSON, `image`, заголовок `X-API-Key: $SK_INGEST_API_KEY`).
Кадр попадает туда же, куда результаты собственного конвейера, — в ближайшую сверку. Опоздавшие кадры отбрасываются.

## Рамки техники в реальном времени

Рамки на живом видео едут за техникой: сервер отдаёт браузеру только координаты (WebSocket `/api/tracks`), видео
не перекодируется — рамки рисует браузер поверх обычного потока. Откуда берутся рамки:

- **Своя модель** (по умолчанию, [app/services/realtime.py](app/services/realtime.py)). Камеру кто-то смотрит — сервер читает
  её видео из шлюза (ffmpeg, до `SK_REALTIME_FPS` = 8 кадров в секунду) и разбирает моделью; камер на экране несколько —
  модель берёт их по кругу, всегда самый свежий кадр (на M4 с CoreML — 6–8 раз в секунду на камеру, пока их две-три).
  Камеру никто не смотрит — её видео не разбирается, рамки идут из анализа кадров раз в 2 с: так учёт работы техники
  ведётся по всем камерам, а процессор не тратится на видео, которое никто не видит. Номер машины между кадрами (`track_id`)
  даёт простой трекер: рамка на новом кадре — продолжение рамки того же типа, с которой больше всего перекрывается.
  `SK_REALTIME_FPS=0` — видео не разбирать (рамки раз в 2 с), `SK_REALTIME_MAX_CAMERAS` (8) — больше камер сразу не читать.
- **Внешний сервис разметки** (детектор + трекер на отдельном компьютере, например с видеокартой) — если задан
  `SK_TRACKER_URL`, рамки берутся от него, своя модель видео не разбирает. Сервис сам читает видео камер из шлюза
  и отдаёт координаты по WebSocket:

```
камера ─RTSP─► шлюз ─WebRTC─► браузер: видео + слой рамок
                 │                        ▲ WebSocket /api/tracks (только камеры, которые пользователю можно видеть)
                 └─RTSP─► сервис разметки ─WebSocket─► сервер
```

- **Сервису:** `GET /api/tracker/cameras` (заголовок `X-Api-Key: $SK_TRACKER_API_KEY`) — какие потоки читать;
  логин шлюза `sk-tracker`, пароль — тот же ключ (только чтение `cam-*`, только TCP). Сервер подключается к его
  WebSocket с заголовком `Authorization: Bearer $SK_TRACKER_API_KEY`.
  Сообщения: `{"camera_id", "ts", "frame_w", "frame_h", "objects": [{"track_id", "type", "confidence", "box"}]}`,
  `box` — проценты от кадра (не доли 0–1 и не пиксели), `x`/`y` — левый верхний угол; `ts` — время кадра с часовым поясом;
  `frame_w`/`frame_h` — размер кадра, по которому посчитаны рамки (у камеры не 16:9 без них рамки съедут).
  Кадры для сверки с планом — `POST /api/ingest/snapshots` тем же ключом; тогда `SK_ANALYSIS_PROVIDER=push`, иначе
  кадры сервиса смешиваются с собственным разбором сервера (сервер об этом предупреждает в ответе и журнале).
- **Проверка сервиса до подключения:** `uv run python -m tools.check_tracker ws://<сервис>:8200/stream --key <ключ>
  --backend http://<сервер>:8100` — формат, рамки, track_id, частота и время кадров, id камер; в конце — что исправить.
- **Если что-то не так:** `GET /api/tracker/status` (администратор, руководитель): откуда рамки (`source`: `model` или
  `service`), сколько пришло сообщений, какие камеры разбирает модель и сколько мс занимает кадр; для внешнего сервиса —
  подключён ли он и последняя ошибка формата (`problem`), в журнале сервера — предупреждение раз в минуту.
  `track_id` различается вместе с типом: экскаватор № 1 и самосвал № 1 — разные рамки.
- **Серверу:** `SK_TRACKER_URL=ws://…/stream`, `SK_TRACKER_API_KEY`, `SK_TRACKER_VIDEO_DELAY_MS` — на сколько браузер
  придерживает видео, чтобы рамка попадала в машину (≈ задержка обработки кадра сервисом); `SK_TRACKER_RTSP_URL` —
  адрес шлюза для сервиса на другом компьютере (например `rtsp://192.168.1.10:8554`). Браузер получает рамки по
  WebSocket `/api/tracks`: токен — первым сообщением (в адресе и журналах его нет), ответ `{"type": "ready"}`; вход
  перепроверяется раз в минуту — отключённый сотрудник теряет поток (код 4401), 4503 — сервер входа не отвечает.
  В боевом запуске (`SK_DEMO_MODE=false`) ключи из примеров и короче 16 символов сервер не примет.
- **Имитация сервиса**, пока настоящего нет — [app/mock_tracker.py](app/mock_tracker.py): рамки из разметки демо-роликов
  плавно «плавают», 10 раз в секунду.

  ```bash
  SK_TRACKER_API_KEY=dev-tracker-key uv run uvicorn app.mock_tracker:app --port 8200     # имитация (в .claude/launch.json — «tracker»)
  SK_TRACKER_URL=ws://127.0.0.1:8200/stream SK_TRACKER_API_KEY=dev-tracker-key uv run uvicorn app.main:app --port 8100
  ```

  В Docker: `SK_TRACKER_URL=ws://tracker:8200/stream SK_TRACKER_API_KEY=dev-tracker-key docker compose --profile tracker up --build`.

## Работы по камерам: сервисы аналитики коллеги (frame-analysis-v1)

Какая работа плана идёт на кадре, определяют два сервиса аналитики коллеги по его контракту — копия в
[docs/frame-analysis-v1.md](docs/frame-analysis-v1.md). Наш бэкенд в нём — «внешний бэк»: владеет объектами, камерами
и планом, отправляет кадр, найденную технику, план и историю и хранит ответы. Сервисы к нам не обращаются.

- **deterministic — «по технике»:** матрица «класс техники → вид работ», история наблюдений и отметки выполнения;
  отдельно — похоже ли, что началась следующая работа, и нет ли отставания по срокам (schedule-rules-v1).
- **vlm_llm — «по снимку»:** VLM смотрит кадр, LLM относит увиденное к работам плана. Думает минутами и стоит денег.

Код — [app/services/analytics/](app/services/analytics) (справочник, журнал наблюдений, сборка запроса, HTTP, проверка
ответа, расписание), API — [app/api/work.py](app/api/work.py); таблицы `analytics_requests`, `analytics_results`,
`observations`. Прежний «сервис этапов» с нашим форматом (все камеры объекта одним запросом) убран — миграция 0008.

**Подключение** — переменные из контракта (с приставкой `SK_` тоже работают):

| Переменная | Назначение |
|---|---|
| `DETERMINISTIC_SERVICE_URL`, `VLM_LLM_SERVICE_URL` | базовые адреса сервисов, без `/v1/analyze/frame`; можно один из двух; не задан ни один — выключено |
| `ANALYTICS_SERVICE_TOKEN` | общий токен: уходит обоим в `Authorization: Bearer …` |
| `ANALYTICS_HTTP_TIMEOUT_SECONDS` | сколько ждать ответ (1020 с: модельные попытки — до 4 × 240 с) |
| `SK_ANALYTICS_INTERVAL_MIN` | раз во сколько минут отправлять свежий кадр каждой камеры рабочей зоны «по технике» (20) |
| `SK_ANALYTICS_VLM_INTERVAL_MIN` | то же «по снимку» — реже, вызовы модели платные (60); кнопка «Определить сейчас» шлёт обоим |
| `SK_ANALYTICS_HISTORY_DAYS`, `SK_ANALYTICS_OBSERVATION_MIN` | окно истории (7 дней) и шаг журнала наблюдений (20 минут) |
| `SK_ANALYTICS_CLASSES` | тип техники → код класса справочника, если он не нашёлся среди кодов и синонимов справочника |

**Что уходит** — `POST {адрес}/v1/analyze/frame`, multipart ровно из двух частей: `metadata` (JSON) и `image` (кадр);
заголовки `Idempotency-Key` = `request_id`, `Authorization`, `Accept: application/json`. Один запрос — один кадр одной
камеры; оба сервиса получают одни и те же байты с одним `request_id`, одновременно.

- **Кадр** — последний снимок камеры (JPEG 1280×720 без рамок), `image_id` — id снимка, sha256 и размеры — от тех же байтов.
- **Камеры** — только рабочих зон: на въезде и складе техника подъезжает, а не работает.
- **Участок** — план объекта у нас одной цепочкой, поэтому участок на объект один: `plan_stream_code = "main"`,
  весь кадр (`roi_bbox = null`).
- **cv** — техника от нашей модели: наши типы → коды классов справочника по явной таблице `CLASS_TABLE`
  ([catalog.py](app/services/analytics/catalog.py)): экскаватор → `Excavator`, самосвал → `DumpTruck`, каток →
  `RoadRoller`, кран-манипулятор → `TruckMountedCrane`, бетоносмеситель → `ConcreteMixerTruck`, бульдозер → `Bulldozer`,
  автокран → `MobileCrane`. Грузовика в справочнике коллеги нет — такую технику не отправляем и пишем об этом в запросе
  (другой справочник — по кодам и синонимам `aliases` или `SK_ANALYTICS_CLASSES`). Рамки — доли кадра
  `[x_min, y_min, x_max, y_max]`, `model_version` — модель, которая нашла технику. Анализ кадра не удался — `failed`.
- **plan** — работы плана (уровень 2) по графику. `stage_id` — **вид работ по справочнику сервисов**, его у каждой
  работы выбирает человек в редакторе плана (по похожему названию подставлять нельзя). Сроки — полночь по Москве:
  начало — в день начала, конец — на следующий день после даты окончания. `revision_id` — отпечаток содержимого:
  любая правка плана — новая версия. Хоть одна работа без вида по справочнику (или выбрана по старой версии
  справочника) — план не отправляется (`plan = null`), причину видно в интерфейсе. Работы без техники
  (`stage_kind = no_class`: геодезия, отселение) тоже идут в план — по ним сервисы следят только за сроками
  и отметками выполнения, по кадрам их не определяют. Сводные этапы справочника (`summary`) в план не идут: у нас это
  этапы плана уровня 1 — группировки работ. Так договорились с коллегой 26.09, сервисы 0.2.0 так и работают.
- **history** — журнал наблюдений: раз в 20 минут кадр каждой камеры записывается без картинки (id снимка, время,
  sha256, техника). Уходят записи камер рабочих зон за 7 дней, не больше 500; если больше — окно укорачивается до
  последних 500 целиком, `complete` остаётся `true`. **progress_events** — отметки руководителя «сделано, %»:
  0 % — `not_started`, 1–99 % — `in_progress`, 100 % — `completed`; время — момент отметки, `actual_*` — `null`
  (точных дат начала и окончания у нас нет).
- **Вид объекта** — `object_type_code`: виды объектов у нас те же, что в «Справочнике видов работ» (жильё, школа,
  детский сад…, дороги); «соцобъект без уточнения», промышленный и «другое» уходят как `null`.

**Ответы.** Каждый проверяется до сохранения: тот же кадр, версия плана, участок, снимок истории, справочник и отпечаток
входа (`input_sha256`), кандидаты — пункты отправленного плана. Не сошлось — это ошибка, а не ответ. Хранятся целиком;
`metadata` (сотни килобайт) остаётся только у последнего запроса каждой камеры. Ход работ по ответам не меняется.
Повторы — только явно повторяемых отказов (`busy`, `not_ready`, `dependency_unavailable`): не больше двух, через 1 и 2 с
или по `Retry-After`. Ответ потерялся (обрыв, тайм-аут) — анализ заново не запускаем, а спрашиваем
`GET /v1/analyses/by-request/{request_id}`: вызов модели мог быть платным.

**Когда отправляем:** в рабочее время объекта — «по технике» раз в `SK_ANALYTICS_INTERVAL_MIN` (20) минут, «по снимку»
раз в `SK_ANALYTICS_VLM_INTERVAL_MIN` (60) минут: свежий кадр камеры, если он новый с прошлой отправки; камеры по очереди. Руководитель и администратор могут отправить сейчас — кнопка «Определить сейчас»
(`POST /api/sites/{id}/work-analysis`, ответы приходят в фоне). Интерфейс (`GET /api/sites/{id}/work-analysis`) показывает
по каждой камере ответы обоих сервисов рядом: работа или «одна из работ», что видно на снимке, почему так; отдельно —
возможное начало следующей работы и возможное отставание. «Победителя» не выбираем.

**Справочник** — `GET /v1/catalog` у сервисов, раз в 10 минут; копия сохраняется в каталоге данных, чтобы план можно
было править, даже когда сервисы не отвечают. Нам — `GET /api/analytics/catalog?siteId=…`: работы для вида объекта.
У сервисов коллеги 0.2.0 — `catalog-cf435bba295909ab953facca`, 377 видов работ и 40 классов техники; `stage_path` —
строка «Раздел / … / Работа». Названия работ повторяются в разных разделах, поэтому в плане список — по разделам.
Демо-план сопоставлен с этим справочником (номера — в `CATALOG_WORKS` в [app/seed.py](app/seed.py)).

**Настоящие сервисы — комплект коллеги 0.2.0** (Docker, Linux/amd64: на Mac с Apple Silicon идёт через эмуляцию).
Запуск — по его README, в каталоге комплекта:

```bash

```

Затем `.env` из `.env.example` с четырьмя своими секретами (`POSTGRES_PASSWORD`, `ANALYTICS_DETERMINISTIC_DB_PASSWORD`,
`ANALYTICS_VLM_DB_PASSWORD`, `ANALYTICS_SERVICE_TOKEN`) и `docker compose up -d`. Сервисы — на `127.0.0.1:18001`
(deterministic) и `127.0.0.1:18002` (vlm_llm). Нашему бэкенду — в `backend/.env` (в git не попадает):

```bash

VLM_LLM_SERVICE_URL=http://127.0.0.1:18002
ANALYTICS_SERVICE_TOKEN=<тот же, что в .env комплекта>
```

Сервису «по снимку» нужен ключ модели — `LITELLM_API_KEY` в `.env` комплекта (в наш бэкенд ключ не попадает). Без ключа
он отвечает `503 not_ready`, и в карточке это видно как «Сервис не готов к работе»; «по технике» от моделей не зависит.
Проверено 26.09 на комплекте: deterministic принимает все наши запросы, сверку сроков и следующей работы делает сам;
vlm_llm с ключом (qwen3.8-27b) отвечает на кадр примерно за 50 с. Модель называет работы нашими id — в карточке они
заменяются названиями из плана. Каждый вызов «по снимку» платный: при отправке раз в 20 минут это 3 вызова в час
на камеру рабочей зоны.

**Имитация обоих сервисов** — [app/mock_analytics.py](app/mock_analytics.py) — для тестов, e2e и показа без Docker.
Справочник у неё тот же, что у сервисов коллеги ([assets/analytics/catalog.json](app/assets/analytics/catalog.json)),

и тот же план годится для обоих. Проверяет запрос строго по контракту (две части, заголовки, sha256 и размеры кадра,
классы, рамки, план, история, идемпотентность) и отвечает правдоподобно, но без моделей: «по технике» — как настоящий
(все работы плана, совместимые с техникой на кадре, по убыванию оценки), «по снимку» — от лица VLM по рамкам.

```bash
uv run uvicorn app.mock_analytics:app --port 8300          # имитация (в .claude/launch.json — «analytics»)
```

**Проверки по контракту:** наш запрос в тестах проверяется JSON Schema коллеги
([docs/frame-analysis-v1.schema.json](docs/frame-analysis-v1.schema.json), Draft 2020-12 с проверкой дат), ответы
имитации — тоже; записанный ответ настоящего сервиса из комплекта (tests/fixtures/analytics) читается и показывается.

**Ещё не согласовано с коллегой:** частота вызовов `vlm_llm` (деньги); шаг истории при лимите 500 наблюдений; годятся ли
отметки «%» как подтверждённый ход работ.

## Камеры по IP

С камерой всегда работаем как с видеопотоком RTSP — так подключаются почти все IP-камеры.
`POST /api/cameras/probe` проверяет адрес (RTSP OPTIONS) и заводит в шлюзе временный поток, чтобы форма показала **живое видео**
камеры ещё до сохранения; `POST /api/cameras` сохраняет камеру, и шлюз сразу начинает забирать видео. Добавлять камеры могут
руководитель проекта и администратор, менять и удалять — только администратор. Пароль камеры шифруется
и наружу не отдаётся; при правке адреса пустой пароль оставляет прежний.

Сервер (и шлюз по его указанию) ходит по введённым адресам, поэтому включена защита от SSRF: только `rtsp`, запрещены служебные
адреса (169.254.0.0/16, адреса метаданных облаков, multicast, 0.0.0.0), в адресе нет управляющих символов.

## Администрирование и журнал действий

Эндпоинты — [app/api/admin.py](app/api/admin.py). Администратор может всё, руководитель проекта — всё, что помечено ниже:

- **объекты** — создать, изменить, назначить прораба (и руководитель), удалить вместе с камерами, планом и отклонениями;
- **календарный план** — укрупнённые этапы и работы с правилом «этап → техника»; **зоны** объекта (и руководитель).
  У работы — вид работ по справочнику сервисов аналитики (`catalogStageId`): сервер проверяет его по справочнику
  и запоминает с версией справочника. Сколько сделано по факту, отмечают руководитель и администратор:
  `PATCH /api/stages/{id}/progress` (прораб только видит). Сколько должно быть сделано по графику, сервер считает сам —
  равномерно по дням этапа (`planProgress` у каждого этапа);
- **сотрудники** — завести, изменить роль и объекты, отключить, удалить, **сменить пароль**. Себя и последнего администратора
  понизить или удалить нельзя. Когда вход через Keycloak, сотрудник, роль и пароль одновременно меняются и в Keycloak;
- **правила «этап → техника»** (только администратор) — добавить (`POST /api/rules`: достаточно названия этапа), изменить
  технику, название и описание, удалить. Правило, выбранное у работ плана, не удаляется: сервер отвечает 409 и называет
  эти работы. Двух правил с одним названием быть не может — у работы плана правило выбирают по названию;
- **отклонения** — любые ответы, включая выдачу и закрытие предписаний.

Каждое действие (и вход в систему, в том числе неудачный) пишется в **журнал действий**: кто, когда, что именно поменялось
(«было → стало»), с какого адреса. Пароли в журнал не попадают. `GET /api/audit` — фильтры по виду действия, сотруднику, тексту.

## Методика сверки

Логика — в [app/services/engine.py](app/services/engine.py), правила ведёт администратор в интерфейсе («Управление →
Правила»). Базовая методика — 9 правил от подготовки площадки до благоустройства
([app/services/methodology.py](app/services/methodology.py)) — ставится в любую новую базу, и с демо-данными, и без них:
сервер ставит её, если в базе ещё нет ни сотрудников, ни объектов, ни правил. Удалённое администратором правило само
не возвращается.

1. Этап объекта берётся из календарного плана по дате проверки; у этапа есть правило: нужная техника (с минимумом) и лишняя.
2. Нужная техника считается **только в рабочих зонах**. Техника на въезде и складе считается подъезжающей.
3. Нехватка и лишняя техника подтверждаются, если повторяются **N проверок подряд** (N задано в правиле; проверка — раз в минуту).
   Проверки ближе друг к другу, чем 0,8 интервала (например, внеочередная после правки правила), считаются за одну.
4. Простой: техника из списка нужной не сдвинулась (IoU рамок ≥ 0,9) на 3+ кадрах за 2+ часа.
5. Видео с камеры нет дольше 10 минут — предупреждение «зона не просматривается».
6. Условие исчезло — предупреждение снимается автоматически (кроме выданных предписаний). Судим только по тому, что видно:
   пока камера молчит, предупреждение не снимается. Камеру выключили или удалили — её предупреждения снимаются с этой причиной.
   Закрытое человеком предупреждение не поднимается снова, пока картина не изменится (пауза в видео — не изменение).
7. **Рабочее время объекта** (в карточке объекта: часы и дни, по умолчанию у нового — 8:00–20:00, пн–сб; у объектов,
   заведённых раньше, — круглосуточно). Вне его технику не сверяем: ночью и в выходные её на площадке нет — это не
   «нет экскаватора» и не «простой». Новые отклонения не заводятся, открытые не снимаются, серии подтверждения прерываются;
   «камера не отвечает» работает и ночью. Кадры сервисам аналитики по расписанию тоже уходят только в рабочее время.
8. **Техника, которую модель не распознаёт** (своя модель на MOCS не знает кран-манипулятор и грузовик): её нехватка
   не становится отклонением — в «План и факт по технике» и в проверке фото она помечена «проверьте на месте», в редакторе
   правил — «модель пока не распознаёт». Список распознаваемой техники — `detectableEquipment` в `/api/meta`.

Каждая проверка пишется в `check_runs` (что увидели, какие отклонения) — решение системы всегда можно проверить.

## Вход через Keycloak (необязательно)

По умолчанию вход локальный (логин/пароль + быстрый вход по роли). Единый вход организации через Keycloak
(OpenID Connect) включается заданием `SK_KEYCLOAK_ISSUER` — тогда бэкенд принимает **и** свои токены (HS256),
**и** токены Keycloak (RS256): подпись проверяется публичными ключами realm (JWKS), роль берётся из realm-ролей
токена, привязка к объектам — из базы по логину (`preferred_username`). Ролями управляют в Keycloak: если роль там
поменяли, она переносится в базу при следующем запросе пользователя. Если Keycloak не отвечает, API возвращает 503,
а не 401 — пользователя не выкидывает из системы.

Запуск Keycloak для разработки (Docker), из каталога `backend/`:

```bash
docker compose -f ../infra/keycloak/compose.yml up -d   # http://localhost:8080, admin/admin
SK_KEYCLOAK_ISSUER=http://localhost:8080/realms/stroykontrol \
SK_KEYCLOAK_ADMIN_CLIENT_SECRET=stroykontrol-dev-backend-secret \
  uv run uvicorn app.main:app --port 8100 --reload
```

У Keycloak своя база PostgreSQL (том `keycloak-db`): сотрудники, роли и пароли, в том числе заведённые в нашей админке,
переживают перезапуск и пересоздание контейнеров. Realm импортируется из файла только при первом запуске; начать с чистого
листа — `docker compose -f ../infra/keycloak/compose.yml down -v`.

Realm `stroykontrol` ([infra/keycloak/realm-stroykontrol.json](../infra/keycloak/realm-stroykontrol.json)) уже содержит
роли `foreman/manager/inspector/admin`, клиент `stroykontrol-web` (public + PKCE), служебный клиент `stroykontrol-backend`
(через него админка меняет сотрудников, роли и пароли), русскую страницу входа, профиль без обязательной почты и
пользователей `prorab / rukovoditel / inspektor / admin` с паролем `demo`. Фронтенд берёт режим из `/api/meta` и показывает
кнопку «Войти через Keycloak» без пересборки. Токен продлевается перед запросами; кнопка «Выйти» завершает и сессию
Keycloak, а истёкший токен — нет (повторный вход пройдёт без пароля, пока сессия Keycloak жива).

| `alerts`, `alert_evidence`, `alert_events` | предупреждения, кадры-доказательства, история ответов |

| `alembic_version` | номер последней применённой миграции |

### Миграции

Структура базы ведётся миграциями Alembic ([migrations/versions](migrations/versions)). Сервер при запуске сам применяет
недостающие миграции — и на SQLite, и на PostgreSQL; данные при этом не трогаются. Поменяли модели в `app/models.py` —
добавьте миграцию и проверьте сгенерированный файл:

```bash
uv run alembic revision --autogenerate -m "что поменялось"   # новый файл в migrations/versions
uv run alembic upgrade head                                  # применить (сервер сделает это и сам при запуске)
uv run alembic downgrade -1                                  # откатить последнюю
```

Тест `tests/test_migrations.py` следит, чтобы миграции и модели не расходились и откатывались в обе стороны.
В Docker команды те же: `docker compose exec backend .venv/bin/alembic upgrade head`.

Базы, созданные до появления миграций: демо-базу сервер пересоздаёт сам, боевую (`SK_DEMO_MODE=false`) не трогает —
останавливается и подсказывает, как пометить её первой миграцией (`alembic stamp 0001`).

## Ограничения прототипа

- Распознавание — модель, обученная на MOCS: кран-манипулятора и грузовика она не знает, Truck считается самосвалом.
  В Docker на Mac кадр ≈ 0,2 с (без CoreML): рамки в реальном времени на 3–4 камерах сразу — 1–2 раза в секунду.
- Конвейер видео живёт внутри процесса API — запускайте один воркер uvicorn.
- Сервисы аналитики коллеги пока на имитации: её справочник небольшой, номера работ выдуманы — с настоящим сервисом
  вид работ у работ плана придётся выбрать заново. Работы без техники (`no_class`) его сервис примет в следующей версии.
- История для сервисов — журнал с шагом 20 минут и не больше 500 наблюдений в запросе: при нескольких камерах рабочих
  зон на объекте в запрос влезает меньше недели.
- Видео проверено на потоках H.264 (демо-ролики через mediamtx); браузеру нужен H.264 без B-кадров — большинство IP-камер так и отдают.

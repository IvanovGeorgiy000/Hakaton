# СтройКонтроль — бэкенд

API сервиса мониторинга строительных площадок по камерам (ЛЦТ 2026, команда «Работяги»).
Кадр с камеры → техника на кадре → сверка с этапом календарного плана → предупреждение об отклонении.

**Стек:** Python 3.12+, FastAPI, SQLAlchemy 2 (async), Pydantic v2, httpx, Pillow; SQLite локально, PostgreSQL в Docker; менеджер пакетов `uv`.

## Запуск

```bash
cd backend
uv sync                                    # зависимости
uv run uvicorn app.main:app --port 8100    # API: http://localhost:8100, Swagger: http://localhost:8100/docs
```

При первом запуске пустая база наполняется демонстрационными данными. Время в них считается от момента запуска,
поэтому стенд всегда выглядит «сегодняшним». Пересоздать базу: `uv run python -m app.seed --reset`.

Весь стенд в Docker (PostgreSQL + API + интерфейс): из корня репозитория `docker compose up --build`,
интерфейс — http://localhost:8080.

Проверки: `uv run pytest` (26 тестов, сеть не нужна; те же тесты на PostgreSQL — с переменной `SK_TEST_DATABASE_URL`), `uv run ruff check app tests`.

### Вход

| Логин | Роль | | Логин | Роль |
|---|---|---|---|---|
| `prorab` (и `prorab2…4`) | прораб, свой объект | | `inspektor` | инспектор |
| `rukovoditel` | руководитель проекта | | `admin` | администратор |

Пароль стенда задаётся переменной `SK_DEMO_PASSWORD` (по умолчанию `demo`) при наполнении базы. В демо-режиме
(`SK_DEMO_MODE=true`) работает вход по роли без пароля: `POST /api/auth/demo-login`. Права проверяет сервер:
прораб видит только свой объект, правила и камеры меняет только администратор, предписания закрывает только инспектор.

## Настройки

Все переменные начинаются с `SK_`, полный список с пояснениями — в [.env.example](.env.example). Главное:

| Переменная | Назначение |
|---|---|
| `SK_DATABASE_URL` | по умолчанию SQLite в `data/`; для PostgreSQL — `postgresql+asyncpg://…` и `uv sync --extra postgres` |
| `SK_SECRET_KEY` | подпись токенов и шифрование паролей камер — **поменяйте вне стенда** |
| `SK_ANALYSIS_PROVIDER` | `mock` — демо-анализатор, `http` — внешний сервис распознавания |
| `SK_CAPTURE_INTERVAL_S` | период автоматической проверки объектов, секунд (`0` — только вручную) |

## Анализ кадров: сейчас мок, позже — внешний сервис

Анализ спрятан за интерфейсом `AnalysisProvider` ([app/services/analysis/](app/services/analysis/)). Остальной код не знает, кто именно нашёл технику.

- **`mock`** (по умолчанию) узнаёт 13 демонстрационных кадров по «отпечатку» изображения и отдаёт их разметку
  из `app/assets/seed/annotations.json`. Незнакомый кадр честно помечается как нераспознанный: выдуманных рамок нет,
  сверка по такому кадру не проводится.
- **`http`** — клиент внешнего сервиса. Включается двумя переменными, код менять не нужно:

  ```bash
  SK_ANALYSIS_PROVIDER=http SK_ANALYSIS_API_URL=http://ml-host:8200/analyze
  ```

### Контракт сервиса анализа

```
POST {SK_ANALYSIS_API_URL}            multipart/form-data
  image      кадр JPEG 1280×720
  camera_id  идентификатор камеры (необязательно)
  taken_at   время кадра, ISO 8601 (необязательно)
Authorization: Bearer {SK_ANALYSIS_API_KEY}    — если ключ задан

200 application/json
{ "model": "yolo11m-construction-v1",
  "detections": [ { "type": "excavator", "confidence": 0.94,
                    "box": { "x": 24.5, "y": 41.5, "w": 46.5, "h": 57.0 } } ] }
```

`type` — один из `excavator, dump_truck, roller, manipulator, mixer, bulldozer, truck, crane` (неизвестные типы пропускаются).
`box` — проценты от кадра, `x`/`y` — левый верхний угол. Готовая заготовка такого сервиса с примером для YOLO:
[tools/analysis_stub.py](tools/analysis_stub.py).

**Push-режим.** Если сервис анализа сам забирает видео с камер, он присылает готовый результат:
`POST /api/ingest/snapshots` (`camera_id`, `detections` — JSON, `image`, заголовок `X-API-Key: $SK_INGEST_API_KEY`).
Дальше общий конвейер: снимок сохраняется, объект сверяется с правилом, обновляются предупреждения.

## Камеры по IP

`POST /api/cameras/probe` проверяет адрес и возвращает кадр для предпросмотра, `POST /api/cameras` сохраняет камеру и сразу
снимает первый кадр. Поддерживаются снимок по HTTP/HTTPS (Basic и Digest, поток MJPEG) и видеопоток RTSP (кадр берёт `ffmpeg`,
в Docker-образе он есть; без него доступна только проверка связи). Пароль камеры шифруется и наружу не отдаётся.

Сервер сам ходит по введённым адресам, поэтому включена защита от SSRF: только `http/https/rtsp`, запрещены служебные адреса
(169.254.0.0/16, multicast, 0.0.0.0), редиректы выключены, размер и время ответа ограничены, ответ обязан быть картинкой.

**Демо-камера.** В демо-режиме сервер сам изображает IP-камеру: `http://127.0.0.1:8100/mock-camera/{1..5}/snapshot.jpg`
(с паролем — `/mock-camera/secure/{n}/snapshot.jpg`). Так добавление камеры по адресу показывается без оборудования.

## Методика сверки

Логика — в [app/services/engine.py](app/services/engine.py), правила редактируются в интерфейсе администратора.

1. Этап объекта берётся из календарного плана по дате проверки; у этапа есть правило: нужная техника (с минимумом) и лишняя.
2. Нужная техника считается **только в рабочих зонах**. Техника на въезде и складе считается подъезжающей.
3. Нехватка и лишняя техника подтверждаются, если повторяются **N проверок подряд** (N задано в правиле) — случайные кадры отсекаются.
4. Простой: техника из списка нужной не сдвинулась (IoU рамок ≥ 0,9) на 3+ кадрах за 2+ часа.
5. Камера молчит дольше 2 часов — предупреждение «зона не просматривается».
6. Условие исчезло — предупреждение снимается автоматически (кроме выданных предписаний: их закрывает инспектор).
   Закрытое человеком предупреждение не поднимается снова, пока картина не изменится.

Каждая проверка пишется в `check_runs` (что увидели, какие отклонения) — решение системы всегда можно проверить.

## Модель данных

| Таблица | Что хранит |
|---|---|
| `users`, `user_sites` | сотрудники, роли, закреплённые объекты |
| `sites`, `zones` | объекты и зоны (`work` / `gate` / `storage`) |
| `cameras` | камеры: источник (`mock` / `http` / `rtsp`), адрес, зашифрованный пароль, состояние связи |
| `stages` | календарный план, два уровня; у работ — ссылка на правило |
| `rules`, `rule_items` | методика «этап → техника»: нужная / допустимая / лишняя, минимум, пояснение, риск |
| `snapshots`, `detections` | кадры и найденная техника (тип, уверенность, рамка в %, движется ли) |
| `check_runs` | журнал проверок объекта |
| `alerts`, `alert_evidence`, `alert_events` | предупреждения, кадры-доказательства, история ответов |

Таблицы создаются при старте (`create_all`). Для промышленной установки нужны миграции (Alembic) — в прототип не входят.

## Ограничения прототипа

- Распознавание — демо-анализатор; настоящая модель подключается по контракту выше.
- Получение кадра по RTSP реализовано через `ffmpeg`, но на живом RTSP-потоке не проверялось (проверены разбор адреса,
  проверка связи по RTSP и вся HTTP-часть).
- Фоновый опрос камер живёт внутри процесса API — запускайте один воркер uvicorn.
